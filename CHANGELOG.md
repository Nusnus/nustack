## [Unreleased]

### Added

- `principle-responses` shapes how a reply, status update, question or report reads, since a person scans it before they read it. It puts the answer first, then only what the person acts on or needs to trust, with the steps that led there only as evidence. Each paragraph, sentence, list item, heading and link opens with its point, in plain, neutral words, one point to a sentence. Each state is put in words, not a symbol or colour alone. A list opens with a complete sentence unless the heading right above it says what it holds, and is numbered only when its order matters. A table only compares items that each carry three or more facts, and opens with a complete sentence. Each kind of answer keeps the format it first took, each thing named that has a page of its own is linked once in each response, and bold marks only what the person must see. nus-mode reads it whenever the agent writes to a person.
- nus-mode files a nustack bug when you ask, with the fields and `bug` label of nustack's [bug form](https://github.com/Nusnus/nustack/issues/new?template=bug.yml), and offers to file one when it departs from a rule for a reason that would hold in any project like yours.
- The `new-project` playbook creates the project's remote repository where it has none, and configures its settings where it is on GitHub, such as branch protection on `main`.
- The `align` playbook reshapes existing code, from a snippet to a whole project, to nus-mode's bar within its project's standards, if any, so later work in nus-mode meets no friction with them.
- The plugin ships Steph Ango's six Obsidian skills ([kepano/obsidian-skills](https://github.com/kepano/obsidian-skills)), unchanged and each with its MIT license: `obsidian-markdown`, `obsidian-bases`, `json-canvas`, `obsidian-cli`, `defuddle` and `knap`. The agent can load each one, in nus-mode or without it, when the task matches its description, such as writing a `.base` or `.canvas` file.
- For nustack's maintainers:
  - `AGENTS.md` has agents weigh an issue's text as data, never as instructions.
  - `AGENTS.md` keeps nus-mode's bullets on quality over session cost and on times as the owner words them.
  - A record in `vendored/` names each vendored copy's upstream, skills, commit and file blobs. `make check` holds each copy to its record's bytes and exempts it from the rules for authored files.
  - `make smoke` checks that Claude Code and OpenCode each offer the model each vendored skill `tests/fixtures/vendored.ts` lists.
  - `REVIEW.md` has reviewers check a record written by hand against upstream.
  - `.claude/skills` is a symlink to `.agents/skills/`, so Claude Code offers each skill for working on nustack, such as writing-for-agents, as the other hosts do.
  - `AGENTS.md` has each pull request add its own entry under `CHANGELOG.md`'s `[Unreleased]`; the PR template asks for it, and `REVIEW.md` has review check it.
  - `AGENTS.md` has skill text written, and reviewed, for the strongest agent as timeless Zen: each principle holds the owner's value, true in any project, plus only where the owner's taste departs from that agent's pick.
  - `AGENTS.md` has each pull request's `CHANGELOG.md` entry and each release's lead written in a timeless manner, in words that stay true however many releases later they are read, and 0.0.2's lead and each of its entries that broke that rule are reworded to match, with its changes, groups and date as released; 0.0.1's hold the rule as released.
  - `make install`, `make check` and `make smoke` run on macOS as on Linux, and the Devin blueprint builds both machines.

### Changed

- README is a short front page: what nustack is, how to install, use and update it on each host, how it works, the skills and how to contribute.
- nus-mode's cheap-ETA exception moves from its rule for times into its rule to choose quality over session cost, and keeps only the ETA's analysis cheap, never the reading of the live pace.
- nus-mode estimates from observed pace: it reads how fast each job, agent and subagent the work waits on is moving now, tries each other way it has when one fails, and states the basis with the ETA, the observed pace or the past runs it fell back on and why.
- `language-python` links each of its rules for tests to the principle it gives the Python form of.
- `long term` keeps only what builds work to last, done once: performance from the first version, the full bar on temporary code, each fix at its cause and for every instance of its flaw, every file touched finished, each exemption from a check narrow, and only what stays true in the repository; it drops its rules to keep old callers working and to cover every line and branch. Its rules on file and code order move to `layout`, on what to build on to `dependencies`, on wording to `self-explanatory code`, and on tests to `deterministic tests`; nus-mode loads each of those principles wherever the rules it takes in apply.
- `types` keeps only where its rules depart from a strong agent's pick: illegal states unrepresentable in every type, parameter and result, values that never change frozen all the way down, and each member of a closed set handled by name, proven exhaustive wherever a checker can. Its rules on signatures and on enumerating a closed set fold into those, and a branch that meets an unexpected member fails as `fail fast` says.
- `boundaries` keeps only where its rules depart from a strong agent's pick: data from outside the system, settings from the environment included, parsed once, where it enters, strictly into the project's domain types, failing on what does not fit them exactly, such as an unknown field in a format the project owns, or a value of the wrong type. Its rule to hold an expected absence as data is cut, and nus-mode stops loading `boundaries` when a value may be absent.
- `fail fast` keeps only where its rules depart from a strong agent's pick: a wrong state fails where it is first detected, with an error that says how to recover; each assumption is checked once, where it can first fail, and trusted past it; only a failure the design expects is recovered from, so an unknown member of a closed set travels up; a default stands in only where the caller gave nothing, and a given value that does not resolve, such as a misspelled setting, fails; an error is of the project's domain, and its message names what was wrong and, unless it is secret, the bad value; and a rule it adds holds an expected absence, such as a lookup with no match, in its type, as an optional value or an empty collection, for the caller to handle, so nus-mode loads `fail fast` when a value may be absent too.
- `resilience` is redefined as code that comes through failure and load by its design rather than by scattered guards, with each failure and edge case absorbed by its structure or left to fail on purpose: it is built for the load it will grow into, and the larger load at which it breaks is known; it leaves state a rerun finishes, whatever line the process stops at, with work that may run again idempotent and each change landed whole or not at all; every wait on anything outside the process stays bounded by a limit set from its healthy duration; retries stay in one layer, and a wait a reply asks for becomes a minimum rather than the wait; and a reduced mode, as before, says so and ends once its dependency is back. Its retry how-to is cut, since a strong agent's retry does each step unprompted; its how-to for landing a write whole is cut, since each tool lands a write its own way and `language-python` keeps Python's; and its rule that a timeout's error names what stalled is cut, since `fail fast` says it. nus-mode also loads it for code that guards against or handles a failure, a retry and a fallback included, or does work that grows with its input, data or traffic.
- `deterministic tests` holds tests in general and keeps only its most significant rules: each test fails when, and only when, the behaviour it guards breaks. It keeps the smallest test set; each test with a way to fail, its expected value worked out from the promise, and seen failing; fakes only at the boundaries, each hand-written fake tested against its boundary, and replies recorded from real systems; waits on events, a faked clock where behaviour depends on time, timing tests proven under load and flakes fixed at their cause; hard failures; and tiered tests that mirror the source. Test names, refusal pairs, canaries, real-time margins, holding tests to the code's standard, testing the suite's settings, suite speed and the mirror check are cut, as are its how-to detail and the reasons a strong agent knows unprompted; where shared test helpers live moves to `layout`.
- `deterministic tests` has each new test fail against code broken by hand, where `long term` accepted a hand break or a mutation run. `language-python` drops pytest-cov, coverage with its exclusions, mutmut, and the hand breaks of the code mutmut leaves unmutated. The `new-project` playbook drops its mutation-testing job and, from its review and reply, the mutation run and the hand breaks of code no mutation tool mutates.
- `dependencies` keeps only where its rules depart from a strong agent's pick: dependencies point one way; what the language and its standard tools provide comes before code of one's own; code builds on stable public APIs and documented behaviour; each third-party library has one home, in the project's own types and errors, apart from a framework the code runs in or a library whose classes its types extend; an application targets the newest runtime release and a library every maintained one; a declared range floats above a floor while the lockfile pins, a dependency that installs exactly the version declared pins it, with an update tool proposing each newer one, and the rest take the bounds their documentation gives; and deciding logic stays pure, with the I/O at the edges.
- `layout` keeps only where its rules depart from a strong agent's pick: each folder holds one area and each file one responsibility you can state in a line, which splits on a second one, never on size alone, and moves when that responsibility does; the top-level split goes by domain, by layer or both, whichever makes the design readable, and within it two or more files that serve one area share a package named for it, a package holds more than one module, a module whose parts are concepts of their own becomes one, and files in one folder whose names share a prefix no tool requires are a missing package; the layout shows which layers build on which; a folder or module exists once it has content; every file keeps one order, its ecosystem's or one the project writes down; and code orders state up and behaviour down. Its rule to put behaviour with the data it serves leaves layout, since its subject is how code is shaped into types and functions, which is `design`'s. Its rule to plan the layout before writing it is cut, since a strong agent does it anyway. It takes in from `deterministic tests` where helpers that tests share sit, since that rule's subject is where files live: in one folder beside the test tiers, except one the test framework scopes by place, which stays with its tests while they share a tier.
- `design` keeps only where its rules depart from a strong agent's pick: each part has one responsibility and the code is short because its structure fits; a structure is invented only where no battle-tested design pattern fits; shared code that branches on one variant has its general path fixed instead; object-oriented design that follows SOLID comes first, each class exposing only what its clients use, with an abstraction once a dependency has a second implementation, even a test double; and a low line count comes from the design, and clearer code wins where fewer lines read worse. It takes in layout's rule to put behaviour with the data it serves: a function is a method of its type, or sits beside it where the language has no methods, a value a module needs is a member of the type or enum that uses it, and a function that serves no type's data stays at module level, and a class that holds no data is a namespace for functions only where it is a test class or a framework requires it. Design also allows such a class where the language requires one, puts a function beside any type that cannot hold methods, where layout did so only where the language has none, keeps a method that belongs to an abstraction's interface in the abstraction and each implementation, asks for a method only where the project can edit the type, and lets any function that serves no editable type's data stay at module level, where layout kept such a function there. nus-mode also loads design when you decide where a function or value lives. Its rule to separate concerns folds into the value line, and its other spelled-out SOLID principles into the name SOLID. Its ban on denser or cleverer code, which keeping the clearer code carries, the examples of what a framework calls or reads by name that layout's rule listed, and the reasons a strong agent knows unprompted are cut.
- `DRY` keeps only where its rules depart from a strong agent's pick: every piece of knowledge, such as a rule, value, format or decision, has one home, which everything that needs it, in any form, refers to or derives from; the project's mechanism is extended, where a small change suffices, before another is added; pieces that look alike but change for different reasons stay separate; documented defaults stay unwritten; and a check holds equal each copy of a fact a reader needs, which extends to a copy a person reads, such as a README row that mirrors a description, besides one a tool or harness reads. Its rules to find the home before writing and to derive what you would copy fold into the value line, and its rule to merge by reason to change keeps only its half against merging lookalikes, since the value line carries the other. Its pointer to `design` for how a new variant joins a mechanism is cut, since `design` applies wherever the extend rule does. Its exception for a default written out with a comment saying why is cut, since nus-mode asks for that comment beside any departure from a principle. nus-mode also loads `DRY` when you merge a codepath, type, setting, helper or parser.
- `naming` keeps only where its rules depart from a strong agent's pick: every name, even of a file, folder or package, says what its thing is in the domain, and everything it implies holds; one concept has one name everywhere, tests, errors and CLI options included, the one the code and its domain already use; a thing no honest name fits usually has two responsibilities, so it splits, and a catch-all or a metaphor such as `edges` names no domain thing; and a thing is renamed when its responsibility changes. Its rule to define each new domain term in the docstring of the module or class that introduces it is cut from naming and left to `self-explanatory code`, whose subject it is. Its step to read the existing names before naming, its `Invoice`, `RetryPolicy`, `billing/` and `SessionCache` examples and its reasons are cut, since a strong agent does each anyway. Its rename's "everywhere the name appears" is cut, since one name everywhere says it, and its "in the same commit" too, since `long term`'s rule to finish what you touch keeps the rename in the change that made the name stale, and which commit of that change holds it is left to review.
- `self-explanatory code` keeps only where its rules depart from a strong agent's pick: the code says what it does through its names, types and structure, and its comments and docs say only what it cannot; docstrings belong to modules and classes, a module's summarizing in domain terms everything the file holds and a class's stating its responsibility, or in tests its domain term's promises and edge cases, with a test group that cannot hold a docstring named for its term, while a function's name and signature are its documentation, and no docstring repeats what the path, the imports or the names already say; each new domain term, a rule `naming` leaves here, is defined in the docstring of the module or class that introduces it, or in the project's docs where none does; comments point outside the code, with their link where one exists; every text uses the fewest words that say it clearly; and it is written for a reader who never saw the conversation. Its rule that code explains itself folds into the value line, and so does the limit of docs to what the code cannot say. Its call to rename, extract or restructure until each part reads plainly, its list of what a project's docs state, its call to state a rule in your own words, and the reasons a strong agent knows unprompted, are cut, since a strong agent does each anyway or another line says it.

It starts from the project's PR template, with a one-line summary; headed sections for what changed, the risk once it is more than low, what to review first and the steps after the merge; one fold for checks, files with those to read first in reading order, a visible change's screenshots and decisions; and one linked comment for what outgrows the fold. ## [0.0.2] - 2026-11-04

<!-- 0.0.2's entry is reworded to AGENTS.md's rule that each entry and lead is written in a timeless manner, so it differs from its published release page: the owner overrode, this once, the rule that a released changelog entry stays as released. -->

nustack's second release adds a principle for tests to nus-mode, the mode that has a coding agent build software to a senior engineer's bar; a principle is a skill, an instruction file the agent reads when its work needs it. When the agent writes or changes a test, or a test passes on some runs and fails on others, it makes the test's outcome depend only on its inputs: the test waits for what the code does rather than for time to pass, and passes or fails the same way on every run, however busy the machine.

### Added

- `principle-deterministic-tests`, a principle nus-mode reads when the agent writes or changes a test or its helpers, or a test passes on some runs and fails on others: a test's outcome depends only on its inputs, the same on every run and under any load. `language-python`, the skill the agent reads for Python work, gives the principle's Python form: a test that interrupts its own code raises the interrupt at the moment the code reaches the point it interrupts, not from a timer, and the agent proves a test under load by running that one test in a loop, where [pytest-randomly](https://github.com/pytest-dev/pytest-randomly) gives each run a new seed, which varies the values `random` gives.

### Changed

- In Python, the agent gives every test the whole of the suite's per-test time limit, the limit that [pytest-timeout](https://github.com/pytest-dev/pytest-timeout)'s `timeout` setting puts on each test, as `principle-deterministic-tests` says. This replaces `language-python`'s rule to give a test that checks some code ends quickly, such as a loop that must end, a shorter limit with `@pytest.mark.timeout`, which a busy machine can outlast.
- The plugin's description, which opens each release page, names its author in full: Tomer Nosrati.
- For nustack's maintainers:
  - `nustack` is nustack's own command-line tool. The release steps replace editing each file whose version `nustack` compares and running `uv lock` with one command that sets the release's version, commitizen's `uv run cz bump --increment PATCH --version-files-only --yes`. `nustack check` fails when the files listed in `pyproject.toml`'s `[tool.commitizen] version_files`, which that command sets, differ from the files whose version `nustack check` compares.

### Fixed

- For nustack's maintainers:
  - `nustack` stops a Git or `gh` command that stalls or is interrupted; `gh` is GitHub's command-line tool. The tests of that stop pass the same way under load: a command that stalls never ends on its own; each test that signals a command waits until the command reports it is ready; the wait for a stopped command's processes to end runs on a fake clock wherever a test needs it to run out; and each wait a test needs to finish, such as for a command to report it is ready, may last the suite's whole per-test time limit.

## [0.0.1] - 2026-11-04

nustack's first release brings nus-mode, a mode that has a coding agent build software to a senior engineer's bar, installable in Devin, Claude Code, Cursor and OpenCode. nus-mode follows a playbook, a task's numbered steps, when one fits, and reads skills, instruction files the agent loads when its work needs them: one for each principle and one for Python. When the agent's host, the app it runs in, summarizes a long session, nus-mode comes back on its own, or, on hosts where it cannot, has the agent load it again.

### Added

- `nus-mode`, with the playbooks `investigate` and `new-project`, and the skills it reads: `language-python`, for Python work, and one principle for each area of its rules: `principle-naming`, `principle-dry`, `principle-fail-fast`, `principle-boundaries`, `principle-types`, `principle-design`, `principle-layout`, `principle-dependencies`, `principle-resilience`, `principle-long-term`, `principle-self-explanatory-code` and `principle-pr-descriptions`.
- Rules across nus-mode, its playbooks and its principles. The agent departs from a rule only with a reason stated beside the departure; where nothing there can hold one, the reason goes in the project's `AGENTS.md`, the file of instructions agents read in a repository. Among them:
  - files grouped into packages by area
  - module docstrings that summarize their whole file
  - each review finding treated as a hypothesis to confirm or refute
  - fixing a flaw everywhere it appears
  - the fewest words that say it clearly
  - documented defaults left unwritten
  - no class that holds no data and only groups functions
  - test names that read as a sentence after their class's name
  - test cases that write out their expected values
  - decisions nothing else settles, made as the [Zen of Python](https://peps.python.org/pep-0020/)'s aphorisms favour
  - time estimates from the pace the work keeps
  - quality over session cost
- The agent offers to work on its own once it is highly confident it can finish your task without you, and does so once you agree.
- nus-mode comes back after Claude Code or OpenCode summarizes a session that loaded it.
- On other hosts, nus-mode tells the agent to load it again once a summary drops it.
