# Release

Each pull request has already added its entry under `CHANGELOG.md`'s `[Unreleased]`, as [AGENTS.md › Pull requests](../../../AGENTS.md#pull-requests) says, so a release titles that section and adds its lead.

1. Run `git fetch --tags origin main`, then create a branch from `origin/main` and check it out. The step is done when the branch is checked out at `origin/main`'s latest commit and `git tag` lists every tag `origin` holds.
2. Run `bun scripts/release.ts bump`, or `bun scripts/release.ts bump <version>` with a version the owner chooses, such as 0.1.0. From a working tree with no changes and an `[Unreleased]` that lists a change, it sets the next patch version, or the one given, in `pyproject.toml`, `uv.lock` and every manifest through `cz bump`, then titles `[Unreleased]` `[<version>] - <date>` below a new empty `[Unreleased]`, with today's date in UTC, which can differ from the local date, and sets the changelog's links; when it refuses, it changes nothing. The step is done when `pyproject.toml`, `uv.lock` and every manifest hold the new version, the command prints `Set version <version> and titled [Unreleased] as [<version>] - <date>` with today's date in UTC, and `make check` passes.
3. Open the entry on its lead, a short paragraph above its first `###` group that tells a reader new to the project what the release brings. Then read the page `bun scripts/release.ts notes` prints, which the release publishes, as a reader new to the project, as nus-mode's Goal says, and fix each friction point in the entry. The step is done when a lead paragraph sits above the entry's first `###` group, `make check` passes, and a cold read of the page `bun scripts/release.ts notes` prints finds no friction point.
4. Commit the changes, then open the release pull request into `main`, titled `chore: release <version>`, its description started from `.github/pull_request_template.md`. The step is done when `git status --short` lists nothing and that pull request is open.
5. Wait until the pull request's required checks pass, Devin Review has reviewed its head commit and left no open finding, as AGENTS.md › Pull requests says, and the owner has explicitly approved the merge after seeing the page `bun scripts/release.ts notes` prints. Then squash-merge it into `main` through every check, never with `--admin`, with a message you write: the pull request's title as its subject, and no `Co-authored-by` or other trailer. The step is done when the required checks have passed on the head commit, Devin Review has left no open finding on it, the owner has approved the merge after seeing the page, and the merge commit on `main` has the subject `chore: release <version>` and no trailer.
6. Run `gh auth setup-git`, which gives Git the credential of the account `gh auth login` signed in, for the https URL of the repository the plugin's manifest names; `bun scripts/release.ts tag` fetches main and pushes the tag there, whatever the checkout's `origin` uses. Then, from a full clone with no changes in the working tree, on any commit whose plugin version main holds, run `bun scripts/release.ts tag`; it refuses a checkout above main's version, whose release pull request has not merged. It checks out the commit on main that set main's version, the release pull request's merge commit however far main has moved on, runs `make check` and `make smoke` on it, then pushes `v<version>` on it, and the release workflow publishes the release from the tag once CI passes on that commit; a rerun once the tag is pushed prints that the repository already holds it, and a failed push names the tag, so a rerun pushes it. It leaves the clone at that commit, detached. The step is done when it prints `Pushed v<version>, on <commit>, which the clone has checked out detached`, or that the repository already holds `v<version>` on `<commit>`, with the merge commit, the release workflow's run passes and the release is published.
