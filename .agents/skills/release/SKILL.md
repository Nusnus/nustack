name: release
description: Cuts a nustack release, from its version bump to its published release page. Use when asked to release nustack, such as "release v0.0.3".
---

# Release

1. Run `git fetch --tags origin main`, then create a branch from `origin/main` and check it out. The step is done when the branch is checked out at `origin/main`'s latest commit and `git tag` lists every tag `origin` holds.
2. Run `uv run cz bump --increment PATCH --version-files-only`. It sets the next patch version in `pyproject.toml`, `uv.lock` and each file `pyproject.toml`'s `[tool.commitizen] version_files` lists, which `nustack check` holds to the files whose version it compares, and makes no commit, tag or changelog entry. `--increment PATCH` keeps the version below 0.1.0, which commitizen would otherwise pick for a `feat` commit in 0.x; for a version the owner chooses, such as 0.1.0, give that version in place of `--increment PATCH`. The step is done when `git status --short` lists exactly `pyproject.toml`, `uv.lock` and the files `version_files` lists as changed, each carrying the new version, and the only problems `make check` names are in `CHANGELOG.md`: that it does not open with the version's entry, and that its links for that version and `[Unreleased]` are missing or wrong.
3. In `CHANGELOG.md`, in the format its header names, retitle the `[Unreleased]` section `[<version>] - <YYYY-MM-DD>` with the release day, add each change since the last release that it misses, and start an empty `[Unreleased]` section above it. Then add or fix each link `make check` names, above the first `##` heading, since `nustack notes` counts a link below an entry as part of that entry. The step is done when the version's entry is dated with the release day and holds every change since the last release, below an empty `[Unreleased]` section, `make check` names no problem in the changelog's titles or links, and each link the step added or fixed sits above the first `##` heading.
4. Shape the entry as the body of the release page, which `nustack notes` prints around it: open it on a lead, a short paragraph that tells a reader new to the project what the release brings, then group its changes under Keep a Changelog's `###` types of change. In each group, list first the changes a plugin user meets, then, where the group has changes that only nustack's own development meets, end on one `For nustack's maintainers:` bullet that nests them. The step is done when a lead paragraph sits above the first `###` group, each group lists its plugin-user changes first and ends on at most one `For nustack's maintainers:` bullet that nests every other change, `make check` passes, and a cold read of the page `nustack notes` prints, as nus-mode's Goal says, finds no friction point.
5. Commit the changes, then open the release pull request into `main`, titled `chore: release <version>`, its description started from `.github/pull_request_template.md`. The step is done when `git status --short` lists nothing and a pull request from the branch into `main` is open, titled `chore: release <version>`, its description started from `.github/pull_request_template.md`.
6. Run `make check`. Then wait until the pull request's required checks pass, Devin Review has reviewed its head commit and left no open finding, as [AGENTS.md › Pull requests](../../../AGENTS.md#pull-requests) says, and the owner has explicitly approved the merge after seeing the release page `nustack notes` prints. Then squash-merge the pull request into `main` through every check, never with `--admin`, with the pull request's title as the commit's subject and the message AGENTS.md › Pull requests asks for. The step is done when `make check` passes, the required checks have passed on the head commit, Devin Review has left no open finding on it, the owner has approved the merge after seeing the page `nustack notes` prints, and the merge commit on `main` has the subject `chore: release <version>` and a message with no `Co-authored-by` line.
7. Run `git fetch origin main`, check out the commit the merge makes on `main`, and run `uv run nustack release-tag v<version>`. Once it passes, tag `v<version>` on that commit, and push the tag. The release workflow publishes the release from the tag. The step is done when `nustack release-tag` passes on the merge commit, the tag on it is pushed, the release workflow's run passes and the release is published.
