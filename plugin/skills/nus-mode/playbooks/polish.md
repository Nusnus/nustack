# Polish

Polish removes as much as it can from a project's code, tests, docs and config, within the project's standards and nus-mode, keeping what the project does for its users, names included as [align](align.md) defines them. A line too dense to read is split, even where that adds lines. Each change holds only its cuts and splits and what the project asks of every change, departing from [long term](../../principle-long-term/SKILL.md)'s *finish what you touch* and *fix the flaw everywhere it appears* so a reviewer can merge it as safe.

1. **Set the scope and run the baseline** by align's *Set the scope* and *Read the standards and run the baseline*, on the path, module or project the user names, with its tests, else the whole project. Done when both done conditions hold, and the record holds the line count of each kind of file in scope.
2. **Cut, with proof.** Read each file in scope against each principle and language skill that applies, and list each cut one justifies and each line too dense to read. Group them into changes, each small enough to review in one sitting. Before each code or config cut or split, pin what users rely on in the behaviour it touches, through each command and kept name, with a check outside the project on inputs that reach each of its outcomes, errors included. Make the cut or split, then break by hand each kept behaviour a cut test guarded. Revert each cut or split whose pin gives a different result, that adds a check or test failure, whose hand break no kept test catches, or that reads worse cold. Done when each file in scope was read so; each listed cut and split is in a change small enough to review in one sitting, or dropped with its reason; each kept code or config one has such a pin; none kept meets a revert condition above; and the record holds each change's net cut of each kind of file.
3. **Review, then open.** Review each change by [new project](new-project.md)'s *Review your work*, making each flaw outside what the change holds a follow-up, and open it as a pull request where the project takes them, else commit its branch. Done when step 2's done condition still holds, *Review your work*'s holds apart from the follow-ups, and each change is open or committed on its branch.

**Reply:** the scope, the line count of each kind of file before and after, each change, each dropped cut and split with its reason, and each follow-up.
