# New project

New project starts a project from nothing. Before any product code, it builds a complete, coherent development environment: the layout, the tools and the standards they enforce. Each later session then spends its effort on its own goal.

1. **Learn what the project does.** Done when a few written lines state its behaviour at the boundary and its domain terms.
2. **Choose the stack and its tools.** Record the stack. For each development job, including building, running, formatting, linting, type checking, testing, mutation testing, commit hooks and CI, pick, for each language or file kind the job applies to, or once for a job that covers the whole project such as commit hooks, the tool its [language skill](../SKILL.md#languages) names or, where none does, the ecosystem's current standard tool, give each choice a one-line reason, and confirm each against its documentation. Record each tool's version wherever the project can declare one, which step 4 makes every machine run. For each package manager and build tool, record instead the bounds [dependencies](../../principle-dependencies/SKILL.md) gives them. Done when the stack is recorded, and each job has one tool for each language or file kind it applies to, or one tool if it covers the whole project, the one its language skill names or, where none does, the ecosystem's current standard tool, confirmed against its documentation, with a one-line reason and a recorded version wherever the project can declare one or, for each package manager and build tool, the bounds dependencies gives them recorded.
3. **Agree the standards with the user.** Propose every standard, at the strictest setting the principles allow, with the tool or check that will enforce it or the reason only review can. Done when each standard was proposed at the strictest setting the principles allow, with the tool or check that will enforce it or the reason only review can, and the user's decision on it is recorded.
4. **Lay out the project** following [layout](../../principle-layout/SKILL.md): create it with the stack's project-creation command, and have each tool create each file it can create; write each file no tool creates as its format's documentation defines it. Declare what step 2 recorded for each tool, as [dependencies](../../principle-dependencies/SKILL.md) says: a version in the files the tool or its package manager reads, and a package manager's or build tool's bounds in the files its documentation names. Version control tracks every file a fresh clone needs, lockfiles included, and ignores each agent host's machine-local files and what the tools rebuild from tracked files, such as build output and caches. Put step 1's lines on behaviour in the project's docs. Name every part as [naming](../../principle-naming/SKILL.md) says, so a part that stands for one of step 1's domain terms takes that term's name. Done when the project, created with the project-creation command and laid out as layout says, installs and runs; each tool created each file it can create, and each file no tool creates follows its format's documentation; what step 2 recorded for each tool is declared, as dependencies says: a version in the files the tool or its package manager reads, and a package manager's or build tool's bounds in the files its documentation names; step 1's lines on behaviour are in the project's docs; every part is named as naming says, each part that stands for one of step 1's domain terms by that term; and version control tracks every file a fresh clone needs, lockfiles included, and ignores each agent host's machine-local files and what the tools rebuild.
5. **Make the tools enforce the standards.** Each tool's config leaves its documented defaults unwritten, as [DRY](../../principle-dry/SKILL.md) says. Write your own check only for a standard no tool enforces, and have it call the tool that owns any format it reads, following [dependencies](../../principle-dependencies/SKILL.md). Where the project has no remote repository, create one where and with the visibility the user picks; push the project to it. One command, run by the commit hooks and CI, runs every check. CI publishes each run's results in the CI system's report, which a PR description can link. Done when no tool's config restates a documented default without the comment DRY asks for; the command passes on the new project and fails whenever one standard the user accepted in step 3 and assigned to a tool or check is broken on purpose and the rest are intact, for each such standard; the project's remote repository holds the pushed project, any new one created where and with the visibility the user picked; the commit hooks and CI both run the command; each check of your own enforces a standard no tool does and calls the tool that owns any format it reads; and the CI system's report shows a run's results.
6. **Write the project's `AGENTS.md` and PR template.** `AGENTS.md` holds how to install and check the project, each standard only review enforces, and this line, so every later session works in nus-mode:

   ```markdown
   Work in this repository in nus-mode: load the skill before you start.
   ```

   Where a host the project uses reads its own instruction file instead of `AGENTS.md`, in every setup or only in some, that file imports `AGENTS.md`. The PR template follows [PR descriptions](../../principle-pr-descriptions/SKILL.md). Done when `AGENTS.md` holds each standard only review enforces and the nus-mode line; the PR template follows PR descriptions; a fresh clone installs and passes its checks by following `AGENTS.md` alone; a new session on the current host loads nus-mode before its first step or, where the agent cannot start one, the host's documentation shows it reads that file; every host the project uses, the current one included, reads `AGENTS.md` in every setup, directly or through an import in its own instruction file; and the environment is committed before any product code.

7. **Configure the remote repository, where it is on GitHub.** A new repository starts on GitHub's defaults, which let a change reach `main` without passing the project's checks. Set each setting the project needs, branch protection on `main` among them; where you cannot set one, walk the user through setting it. Done when the reply lists each setting chosen, branch protection on `main` among them, and each is in place: GitHub's API shows it where your access can read it, otherwise the user confirms it.
8. **Build what the request asks**, reading each principle and language skill that applies. Every commit passes the project's checks as configured: when code fails one, change the code, and change a check only as the user agrees. Done when the project does what step 1 states, each principle and language skill that applies was read, and every commit passed the project's checks as step 5 configured them or as the user agreed to change them.
9. **Review your work.** Read in full each principle and language skill that applied, then read every file you wrote against it. Treat each nitpick as a sign of a design flaw until you trace its cause, and fix each finding at its cause and every other instance of its flaw, as [long term](../../principle-long-term/SKILL.md)'s *fix the flaw everywhere it appears* says. Run each mutation testing tool over the code you wrote in its language, and make a test kill each surviving mutant; where no tool mutates some code, break it by hand and see a test fail. Where no input tells a mutant from the code, exempt it as [long term](../../principle-long-term/SKILL.md) says; where no input tells a hand break from the code, say so in your reply. Then read the whole project cold, as [the goal](../SKILL.md#goal) asks. Done when each principle and language skill that applied was read in full, a full pass over every file and a cold read find nothing, each finding and every other instance of its flaw was fixed at the cause it traced to, each mutation testing tool ran over the code you wrote in its language, every mutant is killed, or exempted as long term says because no input tells it from the code, each piece of code no tool mutates was broken by hand and a test failed on it or your reply says no input tells the break from the code, and the project's checks pass.

**Reply:** the stack and its tools, each standard with the user's decision, the project layout with one line per module, each hand break no input tells from the code, each GitHub repository setting chosen, and each design decision and departure as nus-mode's [standing rules](../SKILL.md#standing-rules) ask.
