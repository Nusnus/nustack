# New project

New project starts a project from nothing and builds its whole development environment, the layout, the tools and the standards they enforce, before any product code.

1. **Learn what the project does.** Done when a few written lines state its behaviour at the boundary and its domain terms.
2. **Choose the stack and its tools.** Record the stack, and pick one tool for every development job, commit hooks and CI included: one for each language or file kind the job applies to, or one for the whole project where the job covers it, the one a language skill names or, where none does, the ecosystem's current standard tool. Confirm each pick against its current documentation. Done when the stack is recorded, and every job has one tool for each language or file kind it applies to, or one for the whole project where it covers it, each the one a language skill names or, where none does, the ecosystem's current standard tool, confirmed against its current documentation.
3. **Agree the standards with the user.** Propose every standard at the strictest setting the principles allow, with the tool or check that will enforce it, or the reason only review can. Done when each standard was proposed at the strictest setting the principles allow, with its tool or check or the reason only review can enforce it, and the user's decision on it is recorded.
4. **Lay out the project.** Create it with the stack's project-creation command, have each tool create each file it can, and write each other file as its format's documentation defines it. Declare each tool's version or bounds as [dependencies](../../principle-dependencies/SKILL.md) says, where the project can. Version control tracks every file a fresh clone needs, lockfiles included, and ignores each harness's machine-local files. Done when the project, created with that command, installs and runs; each tool created each file it can, and each other file follows its format's documentation; each tool's version or bounds is declared as dependencies says, where the project can declare it; and version control tracks every file a fresh clone needs, lockfiles included, and ignores each harness's machine-local files.
5. **Make the tools enforce the standards.** One command runs every check, the tests included; it passes on the new project, and the commit hooks and CI run it. Break, one at a time, each accepted standard a tool or check enforces, and see the command fail. CI publishes each run's results in the CI system's report. Where the project has no remote repository, create one where and with the visibility the user picks, and push the project to it. Done when the command runs every check, the tests included; it passes on the new project and, for each accepted standard a tool or check enforces, fails when that standard alone is broken on purpose; the commit hooks and CI both run the command; the CI system's report shows a run's results; and, where the project had no remote repository, the one created where and with the visibility the user picked holds the pushed project.
6. **Write the project's `AGENTS.md` and PR template.** `AGENTS.md` holds how to install and check the project, each standard only review enforces, and this line:

   ```markdown
   Work in this repository in nus-mode: load the skill before you start.
   ```

   Where a harness the project uses reads its own instruction file instead of `AGENTS.md`, in every setup or only in some, that file imports `AGENTS.md`. The PR template follows [PR descriptions](../../principle-pr-descriptions/SKILL.md). Done when a fresh clone installs and passes its checks by following `AGENTS.md` alone; `AGENTS.md` holds each standard only review enforces and the nus-mode line; every harness the project uses reads `AGENTS.md` in every setup, directly or through an import; a new session on the current harness loads nus-mode before its first step or, where you cannot start one, the harness's documentation shows it reads `AGENTS.md`; the PR template follows PR descriptions; and the environment is committed before any product code.

7. **Configure the remote repository, where it is on GitHub.** Set each setting the project needs, branch protection on `main` among them, and walk the user through each one you cannot set. Done when each setting chosen, branch protection on `main` among them, is in place: GitHub's API shows it where your access can read it, otherwise the user confirms it.
8. **Build what the request asks.** Where code fails a check, change the code, and change the check only as the user agrees. Done when the project does what step 1 states, and every commit passed the project's checks as step 5 configured them or as the user agreed to change them.
9. **Review your work.** Read in full each principle and language skill that applied, and make a full pass, against them, over every file you wrote or changed. Treat each nitpick as a sign of a design flaw until you trace its cause, and fix each finding at the cause you trace. Then run the project's checks, and repeat the full pass until it finds nothing and they pass. Done when each principle and language skill that applied was read in full, a full pass, against them, over every file you wrote or changed finds nothing, each finding was fixed at the cause it traced to, and the project's checks pass.

**Reply:** the stack and each tool with a one-line reason, each standard with the user's decision, the layout with one line per module, and each GitHub setting chosen.
