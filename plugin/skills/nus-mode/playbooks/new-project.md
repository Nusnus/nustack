# New project

New project starts a project that others will use or that outlives the task, and builds its whole development environment before any product code: the layout, the tools, the standards they enforce and the docs. For a project only the user uses, within the task, follow [small project](small-project.md).

1. **Learn what the project does.** Done when a few written lines state its behaviour at the boundary and its domain terms.
2. **Choose the stack and its tools.** Record the stack, and pick one tool for every development job, commit hooks and CI included: one for each language or file kind the job applies to, or one for the whole project where the job covers it, the one a language skill names or, where none does, the ecosystem's current standard tool. Confirm each pick against its current documentation. Done when the stack is recorded; and every job has one tool for each language or file kind it applies to, or one for the whole project where it covers it, each the one a language skill names or, where none does, the ecosystem's current standard tool, confirmed against its current documentation.
3. **Agree the standards with the user.** Propose every standard at the strictest setting the principles allow, with the tool or check that will enforce it, or the reason only review can. Propose the project's license; whether it keeps a changelog and in which format; and where its remote repository lives, on a service that runs the CI step 2 picked, and with what visibility. Done when each standard was proposed at the strictest setting the principles allow, with its tool or check or the reason only review can enforce it; the license, the changelog and the remote were proposed; and the user's decision on each proposal is recorded.
4. **Lay out the project.** Create it with the stack's project-creation command, have each tool create each file it can, and write each other file as its format's documentation defines it. Declare each tool's version or bounds as [dependencies](../../principle-dependencies/SKILL.md) says, where the project can. Version control tracks every file a fresh clone needs, lockfiles included, and ignores each host's machine-local files. Done when the project, created with that command, installs and runs; each tool created each file it can, and each other file follows its format's documentation; each tool's version or bounds is declared as dependencies says, where the project can declare it; and version control tracks every file a fresh clone needs, lockfiles included, and ignores each host's machine-local files.
5. **Make the tools enforce the standards.** One command runs every check, the tests included; it passes on the new project, and the commit hooks and CI run it. Break, one at a time, each agreed standard a tool or check enforces, and see the command fail. Where a check fails on a project with no code yet, such as a test runner with no tests, give it the smallest placeholder the build step replaces. CI publishes each run's results in the CI system's report. Done when the command runs every check, the tests included; it passes on the new project and, for each agreed standard a tool or check enforces, fails when that standard alone is broken by hand; and the commit hooks and the CI config both run the command.
6. **Write the project's docs.** The README states what the project does, at its boundary and in its domain terms, and how to install and use it. `AGENTS.md` holds how to check the project, each standard only review enforces, and this line:

   ```markdown
   Work in this repository in nus-mode: load the skill before you start.
   ```

   Where a host the project uses reads its own instruction file instead of `AGENTS.md`, in every setup or only in some, that file is a symlink to `AGENTS.md`. Keep the skills for working on the project in `.agents/skills/`, and, where a host the project uses reads a project's skills only from its own folder, that folder is a symlink to `.agents/skills/`. Add the license and changelog step 3 agreed, and a PR template that follows [PR descriptions](../../principle-pr-descriptions/SKILL.md). Done when a fresh clone installs by following the README alone and passes its checks by following `AGENTS.md` alone; the README states what the project does, at its boundary and in its domain terms, and how to install and use it; `AGENTS.md` holds each standard only review enforces and the nus-mode line; every host the project uses reads `AGENTS.md` in every setup, and offers each skill in `.agents/skills/`, directly or through a symlink; a new session on the current host loads nus-mode before its first step or, where you cannot start one, the host's documentation shows it reads `AGENTS.md`; the license and changelog are the ones step 3 agreed; the PR template follows PR descriptions; and the environment is committed before any product code.

7. **Set up the remote repository.** Where the project has none, create one on a service that runs the project's CI, where and with the visibility agreed, and push the project to it. Where it is on GitHub, set each setting the project needs, branch protection on `main` among them, requiring CI's check once its first run has reported, and walk the user through each one you cannot set. Done when the remote holds the pushed project, created, where the project had none, on a service that runs the project's CI, where and with the visibility agreed; the CI system's report shows a run's results; and each setting chosen, branch protection on `main` among them, is in place: GitHub's API shows it where your access can read it, otherwise the user confirms it.
8. **Build what the request asks.** Where code fails a check, change the code, and change the check only as the user agrees. Done when the project does what step 1 states, every commit this step made passed the project's checks as step 5 configured them or as the user agreed to change them, and no placeholder step 5 added is left.
9. **Review your work.** Read in full each principle and language skill that applied, and make a full pass, against them, over every file you wrote or changed. Treat each nitpick as a sign of a design flaw until you trace its cause, and fix each finding at the cause you trace. Then run the project's checks, and repeat the full pass until it finds nothing and they pass. Done when each principle and language skill that applied was read in full; a full pass, against them, over every file you wrote or changed finds nothing; each finding was fixed at the cause it traced to; and the project's checks pass.

**Reply:** the stack and each tool with a one-line reason; each standard, the license, the changelog and the remote with the user's decision; the layout with one line per module; and each setting step 7 chose.
