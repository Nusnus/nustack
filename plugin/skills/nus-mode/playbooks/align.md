# Align

Align reshapes code to nus-mode's bar within its project's standards. It keeps what the code does for its callers, names included: each defined name reachable from outside the input, or, for an input in no project, each name the user gives. Each behaviour change a rule demands is a design decision, made once whoever decides agrees. Each change covers only its scope, departing from [long term](../../principle-long-term/SKILL.md)'s *finish what you touch* and *fix the flaw everywhere it appears* so it stays reviewable.

- **A snippet, file or named package** changes only itself, its tests and what its project asks of every change, such as a changelog entry. Step 2 counts only the forms outside it when it finds a standard. Its checks are step 3's tools, and they pass except for the flaws its follow-ups hold. Refused behaviour changes, other changes to what callers can use, project-wide proposals and test layout become follow-ups. For a file or package, whoever decides agrees to each behaviour change in the change's review. A snippet comes back in one reply block that imports only the standard library and what the snippet already imports, so it runs where it came from, and in another form only once the user agrees.
- **An input in no project** follows the first bullet where this one is silent, and skips step 3. Its checks are the formatter, linter and type checker [new project](new-project.md) picks, at the principles' strictest setting. In place of tests, run the code on inputs that reach each branch, and put its change in the reply.
- **A whole project that others decide**: send them step 3's proposals and step 4's plan in one message, and make each change that holds a proposal once they agree.

1. **Set the scope.** Record the input's kind, its project, who decides and its runtime. Who decides is the user for a snippet, else the project's maintainers where others share the project, else the user. The runtime is the lowest version the project declares, else the user's answer, else the oldest release [dependencies](../../principle-dependencies/SKILL.md) has the project target. Count and reshape only authored files. Done when the record holds the kind, the project, who decides, the runtime and each tracked file that is vendored or tool-generated.
2. **Read the standards and run the baseline.** Read each file that states or enforces a standard, such as agent instructions, docs, templates, tool configs, hooks and CI. Where nothing written decides, a form is a standard when more than half of the instances that could differ keep it, unless a principle's own rule, never a language skill's, makes it a flaw. Install the project, or for an input in no project its imports, on step 1's runtime, then run its checks and tests, restoring the tree after each. Done when the install ran on step 1's runtime, the record holds each file read, each standard with its source, each disagreement between sources, and each check's and test's result and count on that runtime, and the tree is restored.
3. **Settle the standards.** Propose to whoever decides:
   - nus-mode's form or rule for each standard it differs from;
   - one rule for each disagreement;
   - each part the project lacks of what [new project](new-project.md) builds: its pick of a tool for each job; *Lay out the project*'s ignores; what *Make the tools enforce the standards* sets up, with CI only where the project has a remote and no new remote; each part of the `AGENTS.md` that *Write the project's `AGENTS.md` and PR template* writes, each harness's own instruction file that imports it and, where the project takes pull requests, its PR template; and, where the project is on GitHub, the settings *Configure the remote repository* sets.

   Set each tool at the principles' strictest setting that spares each kept standard. Done when each case a bullet names has a proposal, and the record holds each proposal's outcome or the answer still pending, each tool's setting, and each kept standard a proposal breaks at every setting.
4. **Plan the changes.** List each flaw in scope against the settled standards, and against nus-mode where they settle nothing. A snippet, file or package is one change. Stage a project's changes in this order: baseline failures; tooling and checks, with their tools' fixes, the first of them adding what step 3 agreed the project lacks; layout, with each check whose fixes move code; code; then the remaining tests and docs. Each project change covers one stage over one area, or one check over its areas, and stacks on each change it waits on. A check exempts each flaw that a later stage, a follow-up or a pending answer fixes, until that flaw is fixed. Done when each flaw is assigned to one change or follow-up, the record holds each project change's stage, areas, base and exemptions, and any whole-project message is sent.
5. **Make the plan's next change.** Before any hand or unsafe code fix, pin the behaviour it touches with a passing test. Run each check's tool over the scope, in its own commit or reply line, until a rerun changes nothing, then fix the rest by hand. Create each file with the tool that creates it, else as its format's documentation defines it. Hold each commit to step 2's baseline on step 1's runtime, and each check you fix or add to passing over the scope and failing on a planted break. Resettle by step 3 each standard a failure or an answer reopens. Done when the change's flaws are fixed; the record holds each tool run's command, its clean rerun and its commit or reply line; each created file came from its tool or follows its format's documentation; each hand or unsafe code fix has a passing test that pins its behaviour, unless it makes a behaviour change the change names; each commit holds step 2's baseline on step 1's runtime; each check you fixed or added passes over the scope and fails on a planted break; in the plan's first tooling change and each change based on it, the project's hooks and CI, where it has them, run step 3's command; and each reopened standard is resettled.
6. **Review, then open.** Review the change by new project's *Review your work* and a cold read, and assign each flaw outside the change to a later change or follow-up. Open each change outside the reply as a pull request where the project takes them, else push or commit its branch; then repeat steps 5 and 6. Done when step 5's done condition still holds, *Review your work*'s done condition holds and the cold read finds nothing, apart from the flaws assigned this way and step 4's exemptions, each agreed GitHub setting is in place, and each planned change is open, on its branch, in the reply or waiting on an answer.

**Reply:** the record and each follow-up.
