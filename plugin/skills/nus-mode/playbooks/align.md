# Align

Align reshapes code to nus-mode's bar within its project's standards. It keeps what the code does for callers, names included. For an input in no project, callers can use each name the user gives; otherwise they can use each defined name reachable from outside the input. Each behaviour change a rule demands is a design decision, made once whoever decides agrees. Each change covers only its scope, departing from [long term](../../principle-long-term/SKILL.md)'s *finish what you touch* and *fix the flaw everywhere it appears* so it stays reviewable.

- **A snippet, file or named package** changes only itself, its tests and the entries its project's process asks of each change, such as a changelog entry. Step 2 counts only the forms outside it when it finds a standard. Its checks are step 3's tools, at settings that spare each kept standard, and they pass except for the flaws its follow-ups hold. Refused behaviour changes, other changes to what callers can use, project-wide proposals, test layout and standards' homes become follow-ups. For a file or package, the change names each behaviour change it makes, and whoever decides agrees to each in its review. A snippet comes back in one reply block that imports only the standard library and what the snippet already imports, so it runs where it came from; it takes another form only once the user agrees.
- **An input in no project** also follows the first bullet, and this bullet wins where the two differ; it skips step 3. Its checks are the formatter, linter and type checker [new project](new-project.md) picks, at the principles' strictest setting. In place of tests, run the code on inputs that reach each branch, and put its change in the reply.
- **A whole project that others decide**: send them step 3's proposals and step 4's plan in one message. A change waits for their agreement where it holds a proposal or where their process asks them to agree first.

1. **Set the scope.** Record the input's kind and its project. Record its runtime: the lowest version the project declares, else the user's answer, else the oldest release of its language's runtime that [dependencies](../../principle-dependencies/SKILL.md) has the project target. Record each tracked file as authored, vendored or tool-generated, and who decides: the user for a snippet, else the project's maintainers where others share the project, else the user. Only authored files are counted or reshaped. Done when the record holds the kind, the project, the runtime, each tracked file's status and who decides.
2. **Read the standards and run the baseline.** Read each agent instruction, doc, PR template, tool config, hook and CI file, recording where they disagree. Where nothing written decides, a form is a standard when more than half of the instances that could differ keep it, unless a principle's own rule, never a language skill's, makes it a flaw. Install the project, or for an input in no project its imports, on step 1's runtime, as its docs or CI do; then run its checks and tests, restoring the tree after each. Done when the record holds each source read, each standard with its source, each disagreement and each check's and test's result and count, the install ran on step 1's runtime as the docs or CI do, and the tree is restored.
3. **Settle the standards.** Propose:
   - nus-mode's form or rule for each standard it differs from;
   - one rule for each disagreement;
   - one command that runs every check, and commit hooks that run it, where the project lacks them;
   - each part the project lacks of [new project](new-project.md)'s `AGENTS.md`, of the host files that import it and of *Lay out the project*'s ignores;
   - where the project has a remote, CI that runs that command, the GitHub settings new project configures and, where the project takes pull requests, a PR template, each where the project lacks it;
   - for each other job that lacks a tool, new project's pick.

   Set each tool at the principles' strictest setting that spares each kept standard. [Home](../../principle-dry/SKILL.md) each standard in its tool's config, else `AGENTS.md` or a guide it links. Done when each case a bullet names has a proposal, and the record holds the outcome of each proposal and of each strictest setting, or the answer still pending, each kept standard that a proposal breaks at every setting, and each standard's home.
4. **Plan the changes.** List each flaw in scope against the settled standards, and against nus-mode where they settle nothing. Stage a project's changes in this order: baseline failures; tooling and checks, with their tools' fixes, ignores and homes, where the first tooling change also adds the missing parts and settings step 3 proposes; layout, with each check whose fixes move code; code; then the remaining tests and docs. A snippet, file or package is one change. A check exempts each flaw that a later stage, a follow-up or a pending answer fixes, until that flaw is fixed. Each project change covers one stage over one area, or one check over its areas. A change that waits on another stacks on it. Done when each flaw is assigned to one change or follow-up, the record holds each project change's stage, areas, base and exemptions, and any whole-project message is sent.
5. **Make the plan's next change.** Before any hand or unsafe code fix, pin the behaviour it touches with a passing test. Run each check's tool over the scope, in its own commit or reply line, until rerunning it changes nothing, then fix the rest by hand. Create each file with the tool that creates it, else as its format's documentation defines it. Hold each commit to step 2's baseline on step 1's runtime, and hold each check you fix or add to passing over the scope and failing on a planted break. Revise the plan, runtime and baseline as failures, answers or tools demand, and resettle each reopened standard by step 3. Done when the change's flaws are fixed, and the record holds each tool run's command, its clean rerun and any commit or reply line, each created file's tool or format, each hand or unsafe fix's pinning test passing, except where the change names the behaviour change it makes, each commit and check held as this step says, the project's hooks and CI, where it has them, running step 3's command, and each revision and resettled standard.
6. **Review, then open.** Review the change by new project's *Review your work*. Assign each flaw outside it to a later change or follow-up. Once it waits only on its review's answers, open each change outside the reply where the project takes pull requests, else push or commit its branch; then repeat steps 5–6. Done when each skill that applies was reread, step 5's checks hold, the review's full pass and cold read find only flaws assigned this way, its runs of step 3's mutation tools, or its hand breaks where no tool mutates the code, meet *Review your work*'s done condition apart from step 4's exemptions, each agreed GitHub setting is in place, set through the API or by whoever decides, and each planned change carries the entries its project's process asks of each change and is open, on its branch, in the reply or waiting on an answer.

**Reply:** the record and each follow-up.
